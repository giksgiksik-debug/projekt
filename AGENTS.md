# Инструкции для ИИ-разработчика — Vibe Coding

Эти правила применяются при работе через ChatGPT, GitHub, Termux и GitHub Actions. Цель — безопасно развивать проект небольшими проверяемыми изменениями.

## 1. Главные правила
1. Сначала изучи проект и связанные файлы, затем меняй код. Не делай выводов по одному фрагменту или скриншоту.
2. Сохраняй существующий стек, архитектуру, соглашения, идентификаторы пакетов и форматы данных. Не мигрируй на другой стек без согласования.
3. Ищи первопричину ошибки; не маскируй её заглушками, фиктивными данными или отключением проверок.
4. Делай минимальные целевые изменения. Не переписывай большие файлы и не форматируй весь проект без необходимости.
5. Не удаляй и не перезаписывай незакоммиченную работу. Не выдумывай результаты сборки, тестов, коммитов, push или скачивания APK.
6. Если пользователь уже разрешил реализацию, после аудита и плана приступай к работе в рамках разрешения.

## 2. Рабочий процесс
### Перед правками
- Определи назначение проекта, язык, framework, версии SDK и способ сборки.
- Прочитай AGENTS.md, README, ТЗ, структуру проекта, конфигурации, тесты и workflow в .github/workflows/.
- Проверь ветку, состояние Git, последние коммиты и незакоммиченные изменения.
- Проследи поток данных через модели, сервисы, хранилища и UI; найди существующую реализацию до создания новой.
- Для больших задач составь приоритетный аудит с доказательствами, рисками и предлагаемыми исправлениями.

### План и реализация
- Составь короткий план и критерии готовности; отдели обязательные исправления от улучшений.
- Меняй небольшими логически связанными порциями; используй существующие компоненты и зависимости.
- Не добавляй зависимости без необходимости; оцени поддержку, лицензию, размер и совместимость.
- Учитывай ошибки, пустые состояния, жизненный цикл, фоновые переходы и граничные случаи.
- При изменении схемы хранения предусмотрите безопасную миграцию и сохранение существующих данных.
- Не подменяй реальные данные устройства расчётными, если требования предписывают прямые показания.

### После правок
- Просмотри полный diff, импорты, типы, nullability, потоки/корутины и обработку ошибок.
- Выполни git diff --check и доступные тесты/статические проверки.
- Убедись, что нет секретов, случайных файлов и незапрошенных изменений.
- Чётко раздели выполненные проверки и те, что не удалось выполнить.

## 3. Git и ветки
1. Перед изменениями проверь: git status --short, git branch --show-current, git log -5 --oneline.
2. Не работай прямо в main/master: используй заданную или принятую проектом рабочую ветку. Не переключай ветку с потерей незакоммиченной работы.
3. Перед изменением существующего файла в локальной среде создай резервную копию. В Termux — обязательно до редактирования. Не включай резервные копии в коммит без требования.
4. После правок проверь git diff --check и git diff.
5. Коммить только необходимые файлы; не используй git add . без проверки состояния.
6. Не делай force-push, не переписывай историю и не удаляй ветки без прямого разрешения.
7. Не коммить токены, пароли, ключи подписи, .env, local.properties и другие секреты.
8. Для DriverEU при продолжении существующей работы используй ветку ble-discovery-final, если пользователь не указал другую. Не переносить это имя на другие проекты.

## 4. Termux и сборка Android
- Не предполагай, что в Termux установлены Java/JDK, Gradle, Python или Perl. Не предлагай команды java, javac, gradle, ./gradlew, python или perl.
- Не устанавливай эти инструменты только ради локальной сборки.
- Android APK собирай через GitHub Actions; не запускай локальную сборку, если она запрещена рабочим процессом.
- Используй доступные Git-команды, просмотр файлов, GitHub и логи workflow.
- Не выдавай ссылку на APK, пока не подтверждены успешный workflow и существование артефакта.

## 5. GitHub Actions
- До изменений изучи workflow, версии инструментов, команды сборки, условия запуска и способ публикации артефактов.
- Не создавай конфликтующий workflow и не обновляй версии Java, Gradle, Kotlin, AGP, Flutter или зависимостей «на всякий случай».
- При сбое найди первую первопричину в полном релевантном логе. Отличай ошибки компиляции, тестов, конфигурации, зависимостей и упаковки.
- Исправляй причину минимальными изменениями и повторно проверяй сборку. Не отключай тесты или проверки для сокрытия ошибки.
- Проверь variant/flavor, имя, путь и тип артефакта. Не раскрывай секреты в логах.
- Сообщай статус запуска только по фактическому результату. Если запуск недоступен, объясни это.

## 6. APK и версии
- После успешной сборки проверь статус workflow и скачай артефакт именно нужной ветки и запуска.
- Проверяй versionCode/versionName и текущие правила именования до повышения версии.
- Не переименовывай файл так, чтобы это ложно представляло версию внутри APK.
- Если рабочий процесс пользователя предполагает Termux, после скачивания скопируй APK в ~/storage/downloads/ и сообщи фактический путь.
- Если APK не скачан или не скопирован, не утверждай обратное.

## 7. Указания по стеку
### Kotlin / Jetpack Compose
Изучи Gradle-конфигурацию и версии Kotlin, Compose и Android Gradle Plugin. Следуй существующей архитектуре состояния и навигации. Проверяй импорты Material 2/3, контексты @Composable, жизненный цикл, разрешения и ограничения фоновых сервисов Android. Не меняй package ID и manifest без необходимости.

### Flutter / Dart
Сохраняй Flutter-архитектуру. Изучи pubspec.yaml, lib/, навигацию, управление состоянием и тесты. Проверяй совместимость пакетов с текущим SDK. Не переписывай Flutter-приложение на Kotlin. Релизный APK собирай через согласованный GitHub Actions workflow.

### Другие стеки
Определи реальный стек репозитория и соблюдай его правила; не переноси особенности одного проекта в другой автоматически.

## 8. Устройства, протоколы, таймеры и UI
- Для данных устройств прослеживай исходный пакет → декодер → модель → UI. Не выдумывай DID, поля, единицы или значения; сверяйся с документацией, дампами и логами.
- Разделяй отсутствующие, устаревшие и ошибочные данные; не показывай фиктивные нули как реальные значения.
- При исчезновении данных проверяй подписки, потоки, тайм-ауты, очистку состояния и переподключение.
- Для длительных таймеров используй корректный источник времени; проверь поведение при изменении системных часов и перезапуске процесса.
- Уведомления должны соответствовать установленным условиям и режимам, без дубликатов при возобновлении приложения.
- UI должен учитывать маленькие/большие экраны, длинные подписи, состояния загрузки/ошибки и ожидаемую навигацию «Назад».

## 9. Критерии готовности
- [ ] Требуемое поведение реализовано, а не только внешний вид.
- [ ] Учтены ошибки, пустые данные и граничные случаи.
- [ ] Существующие данные и архитектура сохранены либо миграция обоснована.
- [ ] Проверены diff и git diff --check.
- [ ] Доступные тесты и GitHub Actions выполнены либо ограничения явно указаны.
- [ ] Нет секретов, лишних файлов и незапрошенных изменений.
- [ ] Коммит/push подтверждены фактическим результатом.
- [ ] APK передан только при успешной сборке и получении артефакта.

## 10. Итоговый отчёт
После задачи сообщай: (1) что обнаружено, (2) какие файлы и поведение изменены, (3) какие проверки реально выполнены, (4) ветку/коммит/push и статус Actions, если доступны, (5) путь к APK только если он реально получен, (6) что осталось непроверенным.

Не обещай работу в фоне и не говори, что результат готов позже. Выполняй доступные действия в текущей сессии и честно описывай ограничения.

## 11. Приоритет требований
1. Прямые указания пользователя в текущей задаче.
2. Актуальное ТЗ и требования проекта.
3. Этот AGENTS.md.
4. Соглашения репозитория и общие рекомендации.

Для потенциально разрушительных или необратимых действий сначала объясни риск и не выполняй их без явного разрешения.
